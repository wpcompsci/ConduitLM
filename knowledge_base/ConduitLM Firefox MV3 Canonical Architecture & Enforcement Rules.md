# Firefox MV3 Foundation for ConduitLM

## A. Technical Rules (Enforceable)

1. **Rule:** Do not rely on in-memory state in the background script beyond a single event cycle.  
   **Applies to:** Background (Firefox MV3 event page).  
   **Enforcement:** The background page is non-persistent and can unload when idle, so any JavaScript variables or state kept only in memory will be lost on unload[\[1\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,should%20use%20the%20storage%20API). Persist important data using extension storage or other persistent mechanisms.

2. **Rule:** Persist all critical state changes immediately to extension storage (or another durable store).  
   **Applies to:** Background.  
   **Enforcement:** Firefox event-page backgrounds do not preserve state in memory once unloaded[\[1\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,should%20use%20the%20storage%20API). If state is not saved (e.g. to browser.storage.local or IndexedDB) as it changes, crashes or unloads will drop it permanently[\[1\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,should%20use%20the%20storage%20API).

3. **Rule:** Use browser.alarms for delayed or periodic tasks instead of setTimeout/setInterval in the background.  
   **Applies to:** Background.  
   **Enforcement:** An event-page background will not remain alive to wait for a timeout if it goes idle. Standard JavaScript timers won’t fire if the page is unloaded, whereas browser.alarms will wake the background at the scheduled time[\[2\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Firefox%20106.%20,Change%20timers%20to%20alarms).

4. **Rule:** Register all runtime event listeners at the top level of the background script.  
   **Applies to:** Background.  
   **Enforcement:** Event-driven backgrounds load on-demand. If listeners (e.g. browser.runtime.onMessage.addListener) are not registered during the initial load, events can occur with no listener to handle them[\[3\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=,getBackgroundPage). Firefox requires listeners to be set up synchronously on startup for them to persist across unloads[\[3\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=,getBackgroundPage).

5. **Rule:** Do not use inline callback properties (e.g. onclick in contextMenus) in a non-persistent background; use event listeners instead.  
   **Applies to:** Background (context menu setup).  
   **Enforcement:** In Firefox MV3 event pages, assigning an onclick handler when creating or updating a context menu item throws an error[\[4\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=alias%20,event%20page%2C%20they%20throw%20synchronously). The extension must use browser.menus.onClicked to handle menu item clicks, typically registering those in a startup or onInstalled event[\[5\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=runtime.getBackgroundPage.%20,event%20page%2C%20they%20throw%20synchronously). Violating this will cause synchronous exceptions and menu functionality failure.

6. **Rule:** Treat background.service\_worker as unsupported in Firefox – use a background script/page approach for MV3.  
   **Applies to:** Manifest (background configuration).  
   **Enforcement:** Firefox does **not** support Manifest V3 Service Workers as background scripts[\[6\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,service_worker). If background.service\_worker is specified alone, the extension’s background script will not run in Firefox (prior to Firefox 121, it failed to start; from 121+, Firefox falls back to a document context)[\[6\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,service_worker). A cross-browser extension should include a "background" script fallback or use preferred\_environment to ensure Firefox uses an HTML/document background[\[7\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,Safari).

7. **Rule:** Include the "scripting" permission and use the MV3 Scripting API for content script injection.  
   **Applies to:** Background (or any script injecting content scripts).  
   **Enforcement:** In Manifest V3, functions like tabs.executeScript() are deprecated in favor of browser.scripting.executeScript() and related methods[\[8\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Scripting%20API). These require declaring "scripting" in the manifest permissions[\[8\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Scripting%20API). If the scripting permission is missing, any attempt to programmatically inject scripts will fail with an error or simply not execute.

8. **Rule:** Only inject content scripts (statically or dynamically) into pages for which the extension has active host permissions (or the activeTab permission for user-initiated cases).  
   **Applies to:** Content scripts and background script (injection logic).  
   **Enforcement:** Firefox will not run or inject a content script in a page if the extension lacks host permission for that page’s URL[\[9\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=A%20content%20script%20is%20a,web%20page%27s%20origin%20are%20granted)[\[10\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=Permissions). Attempts to inject without permission result in the script not running and errors (e.g. “Missing host permission”)[\[10\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=Permissions). Host permissions must be listed in host\_permissions (or granted via activeTab/optional permission) for injection to succeed.

9. **Rule:** Always check browser.runtime.lastError after calling asynchronous extension APIs (especially for injection, tabs, or messaging calls).  
   **Applies to:** All contexts (background, content, etc.).  
   **Enforcement:** Many WebExtension APIs fail silently by setting runtime.lastError instead of throwing. For example, if a content script injection is attempted on a disallowed page or a tab that no longer exists, lastError will contain the error message[\[11\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=If%20the%20recommendation%20to%20register,callback%20is%20called)[\[12\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=work%20around%20this%20issue%2C%20you,callback%20is%20called). Ignoring lastError means failures (permission denied, missing tab, etc.) go undetected, breaking extension logic without obvious clues.

10. **Rule:** Use one coherent message routing scheme and ensure every message expecting a response is handled exactly once.  
    **Applies to:** Messaging (background ↔ content/script ↔ popup).  
    **Enforcement:** If multiple runtime.onMessage listeners compete or if no listener sends a response, messages can be lost or never resolved[\[13\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=algorithm%20%29,back%20to%20the%20message%20sender). Only one listener should respond to a given message type to avoid undefined behavior[\[13\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=algorithm%20%29,back%20to%20the%20message%20sender). Moreover, when an async response is needed, the listener must return a Promise or true to keep the channel alive[\[14\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=To%20send%20an%20asynchronous%20response%2C,there%20are%20two%20options) – failing to do so will drop the response. In short, each request message should correspond to a single intended responder and use the proper async pattern to guarantee a reply.

11. **Rule:** Limit host permissions and content script matches to the minimum necessary domains for ConduitLM’s functionality.  
    **Applies to:** Manifest (permissions) and content script inclusion.  
    **Enforcement:** Overly broad host permissions will prompt the user to grant access to more sites than necessary, and users can revoke permissions that seem excessive[\[15\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=As%20the%20request%20to%20grant,the%20issues%20you%20should%20consider). Also, listing unnecessary domains increases the extension’s attack surface. Firefox’s install prompt (from version 127+) shows the specific host names requested[\[16\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=host_permissions%20and%20optional_host_permissions%20keys,on%20an%20ad%20hoc%20basis)[\[17\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=,permissions%20in%20the%20install%20prompt). If ConduitLM requests \*://\*.google.com/\* but only truly needs docs.google.com and notebooklm.google.com, a security review or user might reject it. Narrow permissions ensure the extension only runs where intended, and Firefox will only allow content scripts on those specified sites[\[10\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=Permissions).

12. **Rule:** Anticipate that users can dynamically grant or revoke host permissions at runtime, and handle both outcomes gracefully.  
    **Applies to:** Background and content scripts.  
    **Enforcement:** In Manifest V3, Firefox (and other browsers) let users toggle site access on or off after installation[\[18\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=Requested%20permissions%20and%20user%20prompts)[\[19\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=,permissions%20in%20the%20install%20prompt). If ConduitLM tries to interact with a site when permission was revoked, calls will fail (e.g. injections won’t run, webRequest listeners won’t fire). The extension must detect missing permissions (via browser.permissions.contains or catching lastError) and prompt the user or disable the feature instead of failing silently[\[20\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=Your%20extension%20can%20check%20whether,them%20might%20also%20be%20helpful).

13. **Rule:** Avoid holding references to web page DOM objects outside of the page context (after the page navigates or closes).  
    **Applies to:** Content scripts (and background, if it receives DOM data).  
    **Enforcement:** Firefox prevents extensions from accessing a page’s DOM once the page is destroyed, to avoid memory leaks. Any attempt to use a DOM node after its frame closes results in a “cannot access dead object” error[\[21\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=Resolving%20,errors). Thus, ConduitLM should extract the data it needs (text, etc.) from the DOM immediately and only pass/store serializable data. Holding on to live DOM elements beyond page lifetime will break when the page unloads[\[22\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=If%20your%20extension%20references%20a,to%20this%20in%20the%20Console).

14. **Rule:** Do not keep the background script active longer than necessary by maintaining open message ports or uncanceled tasks.  
    **Applies to:** Background and content scripts (long-lived connections).  
    **Enforcement:** An open browser.runtime.Port (from runtime.connect) or an open view will prevent Firefox’s event-page background from unloading[\[23\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts#:~:text=%2A%20Non,does%20prevent%20it%20from%20closing). While this can be used intentionally to keep the background alive during a critical sequence, it should be done with caution. Unneeded persistent connections will waste resources and can mask bugs (since the background never truly unloads in development). Always close ports when work is done so Firefox can return the background page to an idle (unloaded) state[\[23\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts#:~:text=%2A%20Non,does%20prevent%20it%20from%20closing).

## B. Rationale (Per Rule)

1. **Rationale – In-Memory State (Rule 1 & 2):** Firefox’s MV3 background uses an event page model (not a persistent script by default). This means the background context is **unloaded when idle** to save resources[\[24\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Firefox%20has%20extended%20support%20for,support%20for%20persistent%20background%20pages)[\[1\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,should%20use%20the%20storage%20API). All JavaScript state (variables, objects) in a background page evaporates when this happens. For ConduitLM, which might be coordinating multi-step ingestion workflows, any transient queue or partial data kept only in memory would vanish unexpectedly. The enforcement of this is implicit: if the extension goes idle or the browser restarts/crashes, unsaved data is gone. Mozilla’s documentation explicitly advises extensions to record state changes to persistent storage in event pages[\[2\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Firefox%20106.%20,Change%20timers%20to%20alarms). By diligently saving state (e.g. when a new web page content is captured or a NotebookLM upload is scheduled), ConduitLM ensures that even if the background is killed and later restarted, it can resume or retry the operation rather than silently dropping it.

2. **Rationale – Timers vs Alarms (Rule 3):** Standard JavaScript timers (setTimeout, setInterval) are tied to the page’s lifecycle – if the page unloads, they stop. In a persistent background (MV2), that was fine; but in MV3 Firefox, the background might unload before the timer fires. browser.alarms is part of the extensions API designed for event-page/SW contexts. Alarms are stored by the browser and will **wake up** the extension at the scheduled time even if the background was unloaded in between[\[2\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Firefox%20106.%20,Change%20timers%20to%20alarms). This is enforced by design: a delayed task in an unloaded event page simply won’t run unless something wakes the page. ConduitLM’s design should therefore use alarms for any scheduled retry or periodic fetch (for example, to retry a failed NotebookLM upload after N minutes). This guarantees the task will run at approximate time, with Firefox reloading the background to handle the alarm event[\[2\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Firefox%20106.%20,Change%20timers%20to%20alarms).

3. **Rationale – Listener Registration (Rule 4):** In an event-driven model, the extension only loads in response to events. Firefox ensures certain events will wake the background *only if* a listener for them was registered when the extension was last active[\[3\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=,getBackgroundPage). For example, if ConduitLM needs to handle incoming messages from content scripts or alarms, it must add those listeners during the initial load (top-level code). If it were to add listeners dynamically (say, after an async operation), those might be missed or not persist after unload. Firefox documentation notes that listeners should be added at the top-level and using a synchronous pattern (not inside asynchronous initialization)[\[3\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=,getBackgroundPage). The “enforcement” is that if not done, events like runtime.onMessage or alarms.onAlarm may never fire because the background won’t wake up – leading to features not functioning without obvious errors.

4. **Rationale – Context Menus and Other Initialization (Rule 5):** MV3 removed persistent backgrounds, which changes how extensions must register UI elements like context menu entries. In MV2, an extension might create a menu item with an onclick callback directly. But in an event page, that approach is invalid. Firefox throws a synchronous error if an extension tries to assign an onclick in an event page context[\[4\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=alias%20,event%20page%2C%20they%20throw%20synchronously). The reason is that the callback would have been a closure in a page that can go away; instead, the extension is expected to use the event-based listener (browser.menus.onClicked). This design forces separation of registration (done at install or startup) and handling (done via a persistent event listener). The enforcement is strict: any misuse (using onclick property in contextMenus.create/update in MV3) immediately throws and does nothing[\[4\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=alias%20,event%20page%2C%20they%20throw%20synchronously). Therefore, ConduitLM must follow the pattern of creating its menus in a startup or onInstalled handler and listening for clicks via the provided event. This ensures the menu remains functional across background unloads (Firefox will re-initialize the menu on browser restart, and the onClicked listener will be there to handle it).

5. **Rationale – Background Service Worker Support (Rule 6):** Chrome’s MV3 mandates a Service Worker as the background, but Firefox’s MV3 implementation diverged. Firefox did **not** initially implement extension service workers, instead continuing with an HTML-based background page (event page) model for MV3[\[6\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,service_worker). As a result, putting "background": { "service\_worker": "bg.js" } alone in your manifest would not launch that script in Firefox (especially in versions \<121)[\[6\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,service_worker). By Firefox 121, the browser at least loads a fallback background page if service\_worker is present, but it still doesn’t run as a true service worker[\[6\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,service_worker). The MDN docs explicitly mark background.service\_worker as "not supported" in Firefox[\[6\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,service_worker). This means ConduitLM, being Firefox-first, should use "background": { "scripts": \["bg.js"\], "persistent": false } (or an HTML page) to define its background. We can still include the service worker key for Chrome, but use the preferred\_environment manifest field to prefer the document script in Firefox[\[25\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=If%20,supported%20in%20the%20major%20browsers)[\[7\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,Safari). The rule is enforced by Firefox simply ignoring unsupported keys – if we tried to rely on SW events (like onInstalled in a service worker context), they wouldn’t run on Firefox at all, breaking extension functionality.

6. **Rationale – Scripting API Requirement (Rule 7):** Manifest V3 introduced the Scripting API to provide more controlled script injection and to remove the ability to inject arbitrary code strings (for security reasons)[\[8\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Scripting%20API). Firefox supports the Scripting API (with the same interface as Chrome) and disables the old methods (tabs.executeScript, etc.) in MV3 contexts. If ConduitLM attempts to use the old functions in MV3, it will either get a runtime error or no effect. For example, the MV3 migration guide notes that you must “rewrite your code to use the Scripting API” and that this API *requires* the "scripting" permission in the manifest[\[8\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Scripting%20API). The enforcement is that without the permission, calls like browser.scripting.registerContentScripts or executeScript will reject, and if the extension tried to use eval’d code injection, it would be blocked by MV3’s CSP (no eval allowed)[\[26\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=capabilities%20to%20register%2C%20update%2C%20and,unregister%20content%20scripts%20at%20runtime)[\[27\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Manifest%20V3%20has%20a%20more,further%20changes%20in%20your%20pages). In short, ConduitLM must include "scripting" in its permissions and use files for content scripts, ensuring compliance with Firefox’s MV3 execution model.

7. **Rationale – Host Permissions for Content Scripts (Rule 8):** In MV3, host permissions are separated and *not automatically granted on install in Firefox until recently*[\[16\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=host_permissions%20and%20optional_host_permissions%20keys,on%20an%20ad%20hoc%20basis)[\[17\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=,permissions%20in%20the%20install%20prompt). Critically, Firefox will only inject a content script into a page if the extension has permission for that page’s origin[\[9\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=A%20content%20script%20is%20a,web%20page%27s%20origin%20are%20granted)[\[10\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=Permissions). This is a security model enforcement: an extension cannot arbitrarily run code on pages the user didn’t consent to. The documentation states content scripts run only when host permissions for that page are granted[\[9\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=A%20content%20script%20is%20a,web%20page%27s%20origin%20are%20granted). If ConduitLM tried to inject a script into, say, https://chat.openai.com without listing it under host\_permissions or obtaining activeTab permission, Firefox would log an error and refuse the injection. The same goes for using the scripting API: as MDN notes, scripting.executeScript requires either activeTab or host permissions for the target tab[\[10\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=Permissions). Thus, ConduitLM’s manifest must enumerate all target domains (and/or use runtime permission requests), otherwise its site adapters won’t load at all. This rule is user-enforced at install time (the extension must declare or request hosts) and by the browser at runtime (calls will error out if missing permission).

8. **Rationale – Checking runtime.lastError (Rule 9):** WebExtensions APIs in Firefox often fail softly. For example, if you call browser.tabs.sendMessage(tabId, msg) and that tab has no content script (or has unloaded), Firefox won’t throw an exception – instead browser.runtime.lastError will be set indicating the message couldn’t be delivered. Similarly, injecting a script into an unauthorized URL sets lastError with a message about missing permissions. If ConduitLM’s code does not check for lastError, it may assume an operation succeeded when it actually failed. This can lead to silent malfunctions: content not captured, messages not delivered, etc., with no logs unless lastError is inspected. The Firefox migration guide specifically illustrates reading browser.runtime.lastError to avoid uncaught errors when creating context menus repeatedly[\[11\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=If%20the%20recommendation%20to%20register,callback%20is%20called)[\[12\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=work%20around%20this%20issue%2C%20you,callback%20is%20called). While that example is about avoiding console warnings, the principle applies broadly: checking lastError turns silent failures into handled ones. Enforcement here is by omission – if you forget to check, you’ll only see an issue if you open the debug console and notice a warning or if your logic breaks downstream because something never happened. ConduitLM should systematically log or handle lastError after critical calls (e.g., injecting scripts, sending messages, performing webRequests) to catch permission issues or other problems early.

9. **Rationale – Message Routing and Responses (Rule 10):** Reliable messaging is crucial for ConduitLM (content scripts need to send data to the background and get acknowledgements, etc.). Firefox’s runtime.onMessage implementation follows the WebExtensions spec: only one response is sent per message. If multiple listeners each call sendResponse or return a Promise, only the first one wins and others are ignored[\[13\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=algorithm%20%29,back%20to%20the%20message%20sender). Also, if a listener does not indicate it will respond asynchronously, the sendResponse becomes invalid after the listener returns. MDN explicitly warns that adding async to an onMessage listener makes it always return a promise, potentially blocking other listeners and causing unexpected behavior[\[28\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=Warning%3A%20Do%20not%20prepend%20,sendResponse%28true)[\[29\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=The%20,a%20Boolean%20or%20a%20Promise). The rule about using one listener per message type and ensuring a proper async response protocol is to avoid these traps. If ConduitLM accidentally registers two listeners for the same message (perhaps one in the background and one in a popup both listening to runtime.onMessage), the order is not guaranteed[\[30\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=Note%3A%20Avoid%20creating%20multiple%20,listeners%20fire%20is%20not%20guaranteed) and one might preempt the other’s ability to respond. The enforcement is that if two responses are sent, the sender will receive one and the other will be dropped, likely leading to an undefined or null response on the sender side. Similarly, if no listener responds at all, the sender’s promise will hang indefinitely. By design, Firefox will *not* throw an error in these cases; it’s the extension developer’s responsibility to follow the contract. Therefore, ConduitLM should structure messaging such that exactly one part of the extension handles a given request and uses the correct pattern (return true or returning a Promise) to signal an async response[\[14\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=To%20send%20an%20asynchronous%20response%2C,there%20are%20two%20options). This will guarantee that content scripts always get a definitive reply (success or failure) from the background.

10. **Rationale – Least-Privilege Permissions (Rule 11):** Firefox, starting in version 127, shows users a prompt listing the specific hostnames an extension requests access to[\[16\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=host_permissions%20and%20optional_host_permissions%20keys,on%20an%20ad%20hoc%20basis). If ConduitLM requests broad patterns (like all of \*.google.com) when it only needs a subset, users might balk or Mozilla’s reviewers might object. Additionally, requesting extra permissions increases the chance a user will remove or disable an extension’s access to certain sites (since MV3 allows revocation). By limiting host\_permissions and content script matches to exactly the sites ConduitLM needs (e.g. https://chat.openai.com/\*, https://www.youtube.com/\*, https://docs.google.com/\*, etc.), we reduce the risk of permission revocation and demonstrate compliance with least-privilege principles[\[15\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=As%20the%20request%20to%20grant,the%20issues%20you%20should%20consider). This is not only a security recommendation but also a functional one: if a user sees the extension listed on a page it wasn’t intended for (because of an overly broad pattern), they might revoke access globally. Firefox’s enforcement is partly user-driven (permissions UI) and partly technical: content scripts won’t run on sites not in the manifest or granted by the user[\[10\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=Permissions). So by narrowing scope, we keep ConduitLM focused and reliable on its target sites.

11. **Rationale – Dynamic Permission Handling (Rule 12):** MV3’s big change is making host permissions optional at runtime in many cases[\[18\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=Requested%20permissions%20and%20user%20prompts). Firefox allows users to flip an extension’s host access on or off without reinstalling – for example, via the extension’s toolbar icon or the add-on manager, a user can say “restrict this extension to only work on click” or remove a previously granted host. This means ConduitLM can’t assume that because a domain was in the manifest, it always has access. The extension should detect a failure that indicates lack of permission. For instance, if browser.tabs.sendMessage to a Google Docs tab yields lastError about missing host permission, ConduitLM should realize the user has disabled its access and perhaps call browser.permissions.request({origins: \[...\]}) to prompt re-granting[\[20\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=Your%20extension%20can%20check%20whether,them%20might%20also%20be%20helpful). The design from Mozilla’s side encourages this check-request pattern: they note extensions should “check for the availability of expected host permissions and request them if necessary”[\[31\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=As%20users%20can%20revoke%20host,and%20request%20them%20if%20necessary). If ConduitLM didn’t do this, it might simply not function on a site and the user wouldn’t know why. From a reliability standpoint, handling the permission being absent is essential for a good UX (e.g., showing a polite message: “ConduitLM needs access to this site – please enable site access”).

12. **Rationale – Dead Object Errors (Rule 13):** Firefox (and other browsers) implement protective measures to avoid extensions leaking memory or holding references to web content after it’s gone. The "can't access dead object" error in Firefox is a hallmark of an extension trying to use a DOM node from a page that was already unloaded or navigated away[\[21\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=Resolving%20,errors). In ConduitLM’s context, suppose a content script grabs some elements (say a list of messages on ChatGPT) and sends them to the background. The background should not keep the raw Element references; instead it should take the text or needed attributes and store those. If for some reason a DOM object does need to be passed (which is uncommon since structured cloning typically doesn’t allow actual Node objects), it would become unusable once the page is closed. Firefox enforces this by making that object a “dead proxy” – any access logs an error[\[22\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=If%20your%20extension%20references%20a,to%20this%20in%20the%20Console). The guidance from Mozilla is to *store data, not live objects*, if you need to access it later[\[22\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=If%20your%20extension%20references%20a,to%20this%20in%20the%20Console). For ConduitLM, that means the content script should extract innerText, hrefs, etc., and send those primitive values or serializable data structures to the background for ingestion. This ensures that even if the user navigates away or closes the tab, ConduitLM isn’t left holding invalid references. It’s both a memory safety practice and a functional necessity to avoid runtime errors.

13. **Rationale – Background Longevity (Rule 14):** One advantage of event-page backgrounds is efficiency, but sometimes extensions may *accidentally* keep them alive. In Firefox, as noted, an event page remains loaded as long as any message port is open or a UI view is showing[\[23\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts#:~:text=%2A%20Non,does%20prevent%20it%20from%20closing). For example, if a content script opens a long-lived connection to the background (using browser.runtime.connect) and never closes it, the background script won’t suspend. This defeats the purpose of MV3’s design (which is to unload idle extension contexts) and can also hide bugs: the developer might not realize they’re effectively running a persistent background and thus relying on in-memory state that won’t survive a true unload. The rule is to close ports when done (or never open them unless needed). ConduitLM might use a persistent port during an active multi-step interaction (to ensure the background doesn’t unload mid-process), but once finished, it should disconnect. Firefox doesn’t forcibly close ports; it leaves it to the extension. The “enforcement” here is performance-related – an always-alive background might be noticed by users (in about:performance or just via battery usage) or flagged during review if it appears to be abusing the model. It’s a best practice to only keep the extension awake when required. In summary, manage ports and tasks intentionally: keep the background alive only for as long as needed to complete ingestion tasks, and allow it to suspend afterward to comply with MV3’s lifecycle intent.

## C. Common Failure Patterns

1. **Symptom:** **Missing or lost data/state** – e.g. the extension forgets which pages to ingest or loses track of queued content after some time or after a browser restart.  
   **Root cause:** Relying on in-memory variables in the background script (violating Rule 1). In Firefox MV3, the background event page unloads when idle, clearing any unsaved state[\[1\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,should%20use%20the%20storage%20API). If ConduitLM kept a list of “to-ingest” items only in a JavaScript array, it will reset when the background is reloaded. This can also happen if the browser crashes or updates.  
   **How to confirm:** Check Firefox’s about:debugging or extension debugger – if browser.runtime.onInstalled or onStartup fires unexpectedly during usage, it indicates the background was unloaded and then re-initialized. Also, adding console logs in the background’s global scope will show multiple initializations if it’s unloading/reloading. Another clue is to simulate a suspend: after a period of inactivity, try to trigger an extension action and see if prior state is gone (if yes, the background likely unloaded).  
   **ConduitLM prevention:** Always save important state changes to durable storage (e.g., call browser.storage.local.set() whenever a new page capture is added to the queue). Implement restoration logic on startup – e.g., on extension start, load any queued items from storage. Use browser.runtime.onStartup or an initialization routine to recover state. For queued NotebookLM tasks, ConduitLM could also use browser.alarms to schedule persistent retries, so even after a restart, an alarm will wake the extension to resume processing[\[2\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Firefox%20106.%20,Change%20timers%20to%20alarms).

2. **Symptom:** **Content script not running on a target page** – for example, when visiting ChatGPT or YouTube, nothing happens (no logs from content script, extension features don’t activate).  
   **Root cause:** Missing host permission or incorrect match pattern (violating Rule 8 or Rule 11). If the site isn’t listed in host\_permissions (or was revoked by the user), Firefox will not inject the content script[\[9\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=A%20content%20script%20is%20a,web%20page%27s%20origin%20are%20granted)[\[10\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=Permissions). Alternatively, the match pattern in the manifest could be wrong (e.g., a slight mismatch in URL, such as using http:// instead of https://, or missing a subdomain). In MV3, until Firefox 127, host permissions in manifest.json weren’t even prompted to the user[\[16\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=host_permissions%20and%20optional_host_permissions%20keys,on%20an%20ad%20hoc%20basis) – so the extension might silently not have permission if the user didn’t manually grant it post-install.  
   **How to confirm:** Open the extension’s **Browser Console** or the page’s Web Console and look for errors. A common error is: “Error: Missing host permission for the tab” or similar when the background attempts to inject a script or message a content script. Also, go to **about:addons** → ConduitLM → “Preferences” (or “Manage”) and check the “User Permissions” section – Firefox may show toggles for site access. If the site is listed as “no access”, that’s the issue. Using browser.permissions.contains({origins: \["\<site\>"\]}) in the background console can also confirm if the extension currently has permission[\[20\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=Your%20extension%20can%20check%20whether,them%20might%20also%20be%20helpful).  
   **ConduitLM prevention:** Define precise host\_permissions for all required domains in the manifest, and include fallbacks like the activeTab permission if appropriate for one-time injections. If using optional permissions, make sure to call browser.permissions.request at runtime before injecting a script into a new domain[\[20\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=Your%20extension%20can%20check%20whether,them%20might%20also%20be%20helpful). Also, double-check match patterns: e.g., use "https://chat.openai.com/\*" (with HTTPS and trailing /\*). Testing on each target site with the extension loaded will quickly reveal any pattern mistakes. ConduitLM can also implement a startup self-test: attempt a trivial script injection on each expected domain (perhaps via an invisible tab or a permissions check) and log a warning if it fails, guiding developers to any misconfiguration.

3. **Symptom:** **Messaging timeouts or one-way communication** – a content script sends a message and never gets a response, or the background sends a message to a content script and nothing happens (no reply, possibly an error like “Could not establish connection. Receiving end does not exist.”).  
   **Root cause:** Improper message handler setup or asynchronous response not handled (violating Rule 10). A typical case is forgetting to return true or a Promise in a runtime.onMessage listener in the background when you intend to respond asynchronously. The result is that the sendResponse channel is closed prematurely[\[14\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=To%20send%20an%20asynchronous%20response%2C,there%20are%20two%20options), so when the background eventually tries to call sendResponse or resolve a promise, it fails silently. Another scenario is if the content script isn’t injected (as above) – then runtime.sendMessage from the background has no listener, yielding a “receiving end does not exist” error.  
   **How to confirm:** Look at the extension’s background console for browser.runtime.lastError messages after sending a message. If you see no errors, check the content script console: the promise returned by browser.runtime.sendMessage might be stuck pending. In debugging, add console logs in each onMessage listener to verify it ran. If the background listener runs but the content script never sees a response, likely the listener did not properly keep the messaging channel alive. Additionally, if multiple listeners might handle the same message, add logs to each to see if one is intercepting it. Firefox will also drop a console warning if an error is thrown in a listener or if an asynchronous response is attempted without the proper return protocol.  
   **ConduitLM prevention:** Follow a strict messaging pattern. For example, define a single message routing function in the background that examines message.type and handles all expected message types (others get ignored or a default response). In that function, if any work needs to be done asynchronously (like waiting for a network response from NotebookLM), **return a Promise** from the onMessage listener[\[14\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=To%20send%20an%20asynchronous%20response%2C,there%20are%20two%20options). This way, Firefox knows to keep the channel open until the Promise resolves with a result (or is rejected). Test this by sending test messages and ensuring the sender’s promise resolves with the expected value. Also avoid having more than one background listener for messages – consolidate logic so that only one piece of code calls sendResponse/returns a result for each message. If ConduitLM has a popup or other scripts that also listen for messages, ensure they listen for distinct message types or use runtime.connect (ports) for dedicated channels to avoid clashing. Essentially, design messaging such that every request has exactly one response and every response is either sent synchronously or via a kept-alive async handler.

4. **Symptom:** **Context menu entries not appearing or not functioning when clicked.** For instance, ConduitLM adds a right-click menu item “Ingest with NotebookLM” on certain pages, but it doesn’t show up, or it shows but clicking it does nothing.  
   **Root cause:** Misregistration of context menu in an MV3 background (violating Rule 5). If the extension tried to create a context menu item with an onclick callback in the background script, Firefox will throw an error and not create the item[\[4\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=alias%20,event%20page%2C%20they%20throw%20synchronously). If the item was created without error (e.g., during installation) but clicking it doesn’t work, it may be because the extension didn’t register a browser.menus.onClicked listener, so the click goes nowhere. Another possibility is the menu was created in a persistent way that doesn’t persist across restarts (if not using onInstalled as recommended, the menu might disappear when the background unloads).  
   **How to confirm:** Open **about:debugging** and inspect the extension, then check the Console for errors during extension startup or when right-clicking. A telltale sign is a logged error like “Property onclick cannot be used in menus.create, replace with an onClicked event listener”[\[4\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=alias%20,event%20page%2C%20they%20throw%20synchronously). Also, using the Browser Console, call browser.menus.getAll() to see if your menu item is registered. If it’s missing, the creation failed. If it exists but click does nothing, verify if browser.menus.onClicked.hasListener(yourListener) returns true in the background (or simply add a console.log in the onClicked handler to see if it fires).  
   **ConduitLM prevention:** Always create context menu items in a browser.runtime.onInstalled (or on startup) handler. Do not use the onclick parameter; instead, use browser.menus.onClicked.addListener in the background to handle activation[\[5\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=runtime.getBackgroundPage.%20,event%20page%2C%20they%20throw%20synchronously). Test by restarting the browser to ensure the menu persists and that clicking it triggers the intended logic. If the menu should only appear on certain sites, use the documentUrlPatterns or targetUrlPatterns in the create call rather than adding/removing dynamically on each page load (which would be unreliable with an event background). Following Mozilla’s MV3 guidance ensures the menu is reliably present and wired to your handler across extension lifecycles.

5. **Symptom:** **“TypeError: can't access dead object” errors in console after a page is closed**, often accompanied by a stack trace pointing to ConduitLM’s content script or background script. This might occur after navigating away from a page that ConduitLM was interacting with.  
   **Root cause:** The extension is attempting to use a DOM object that is no longer alive (violating Rule 13). This often happens if a content script stored a reference to a webpage element in a global variable or sent a message with a complex object that included DOM nodes. Once the user navigates or closes the tab, those objects are “dead”. Firefox explicitly marks them as such to prevent misuse[\[21\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=Resolving%20,errors). If ConduitLM, for example, retains a reference to a \<div\> that contained an article’s text, and later tries to read from it after the tab is closed, it will trigger this error.  
   **How to confirm:** The error message itself is quite clear in Firefox’s console. It will name a file from the extension and a line number where a dead object was accessed. Identify what that object was (e.g., if the code was element.textContent at line X, then element was likely from a now-closed page). You can reproduce by performing the sequence: capture content on a page, then close the tab before ConduitLM finishes processing that content (or simulate a delay, then navigate away). If the error appears consistently after tab closure, it confirms the extension held onto page data incorrectly.  
   **ConduitLM prevention:** Never assume the page DOM is accessible after the user leaves the page. Content scripts should extract the needed information while the page is active and send only plain data (strings, JSON, etc.) to the background. The background script, in turn, should not store raw DOM elements from content scripts. If some processing needs to happen on the DOM, do it within the content script context and send the result. For example, instead of sending a DOM node for the NotebookLM ingestion, send the innerHTML or text of that node. If ConduitLM uses MutationObserver or other DOM listeners, ensure they disconnect on page unload (though Firefox’s extension framework will usually clean these up on content script destruction). Essentially, by the time a tab is closed or navigation occurs, ConduitLM should have all necessary info in a serialized form. Following this pattern avoids “dead object” errors entirely[\[22\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=If%20your%20extension%20references%20a,to%20this%20in%20the%20Console).

6. **Symptom:** **Background script works in Firefox during development, but extension fails in Chrome (or vice versa) for MV3-specific reasons** – e.g., the extension loads but nothing happens in Chrome, or some API calls in Firefox behave differently.  
   **Root cause:** Divergent MV3 behaviors between Firefox and Chrome not accounted for – such as the background script environment. Perhaps ConduitLM’s background code assumes window and DOM APIs are available (which is true in Firefox’s event page, but **not** in Chrome’s service worker context). Or the code might be using chrome.scripting correctly but didn’t include chrome.runtime.onInstalled in Firefox (relying on SW onInstall event which Firefox doesn’t emit). These cross-browser differences can lead to one environment silently failing.  
   **How to confirm:** If possible, load the extension in Chrome (or use Chrome’s extension test tools). See if errors appear in the Chrome extension service worker console (chrome://extensions \-\> inspect service worker). For Firefox-first issues, examine whether the manifest has both background.scripts and background.service\_worker. If the extension was only tested on Firefox with background.scripts, on Chrome it might not run at all because Chrome expects a service\_worker key. Conversely, if the code uses any DOM-specific calls in background, Chrome’s console would log errors like “document is not defined”.  
   **ConduitLM prevention:** Develop with a **cross-browser mindset**. Use the browser API namespace (Firefox supports it natively; in Chrome it’s aliased or use polyfill) and avoid using any global objects not guaranteed in both environments. One approach is to include both background types in manifest with "preferred\_environment" set appropriately[\[32\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=An%20,environments%20in%20order%20of%20precedence)[\[7\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,Safari), as shown in MDN’s example, so each browser picks what it supports[\[33\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=When%20the%20extension%20is%20executed%2C,this%20happens). In the code, avoid using window, document, or other DOM globals in the background script; if needed, guard them or limit such usage to Firefox via runtime detection. Ideally, structure ConduitLM’s background logic to be agnostic to being an event page vs service worker – for instance, use browser.storage (works in both) instead of window.localStorage (not in SW), and use alarms and messaging which work uniformly. Regularly test in both Firefox and Chrome during development to catch these issues early. While Chrome-specific concerns are slightly outside the Firefox-first scope, mentioning them ensures ConduitLM’s foundation is robust across browsers, given that part of the architecture is shaped by Firefox’s current lack of SW support.

## D. Design Implications for ConduitLM

### Site Adapter Model Constraints (Content Scripts on Each Site)

ConduitLM’s architecture will include site-specific content scripts (adapters) for platforms like ChatGPT, Google Gemini (if applicable), YouTube, Google Docs, and NotebookLM’s interface. Firefox’s MV3 constraints mean these content scripts must be registered with appropriate host permissions and in a manner that ensures reliability:

* **Manifest-declared vs Dynamic:** For critical sites, it’s safer to declare content scripts in the manifest with "matches" patterns for each target site. Manifest scripts in MV3 Firefox will automatically run when the page loads (given permission) and persist across sessions[\[34\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=Content%20scripts%20loaded%20with%20scripting,request%20and%20do%20not%20persist). This reduces complexity – the browser takes care of injecting them every time. Dynamic injection (using scripting.executeScript when needed) could still be used for optional sites or on-demand features, but it adds the overhead of permission checks and error handling at runtime. ConduitLM can mix both: e.g., always inject into known static pages (ChatGPT, NotebookLM) via manifest, while using on-demand injection for pages that require user initiation (maybe a generic “ingest this page” feature).

* **Optional Permissions for Adapters:** If not all users will use all adapters (for instance, a user might want to ingest from YouTube but not grant access to Google Docs), ConduitLM could use optional\_host\_permissions. Each adapter script can be tied to an optional permission. Firefox will initially not inject those scripts until the permission is granted by the user. This requires designing a flow to request permission when the user first tries to use that adapter[\[20\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=Your%20extension%20can%20check%20whether,them%20might%20also%20be%20helpful). The adapter modules should be resilient to not being active – e.g., the extension UI might show “Enable Google Docs ingestion” and call browser.permissions.request({origins: \["https://docs.google.com/\*"\]}) when clicked. The architecture should treat adapters as plugins that can be turned on/off at runtime by the user’s permission settings.

* **Isolated World and Adaptation:** Each content script runs in an isolated environment within the page[\[35\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=DOM%20access). They can interact with the page’s DOM but not directly call page JS functions. ConduitLM’s adapters should therefore focus on DOM extraction (e.g., grabbing text, fields, or using the platform’s public APIs if available) rather than trying to invoke page scripts. If an adapter needs to call page logic (maybe to open a menu or scroll), it might inject a \<script\> tag into the page (which runs in page context) or use window.postMessage. However, such techniques can be fragile and should be minimized. The design should aim for **passive scraping**: reading the content and state from the DOM that the user sees, which is usually sufficient for ingestion. This avoids complex script injection logic and works consistently on Firefox.

* **Adapter Independence and Failure Containment:** Because Firefox allows revoking permissions per host, one adapter failing (due to permission loss or site changes) should not break the whole system. ConduitLM’s background should be designed to handle messages from content scripts individually – e.g., if the YouTube adapter never activates (no permission), the background might never receive YouTube data, which should be fine. Each adapter could register itself with the background upon loading (sending a “Hello from X adapter” message), and the background keeps track of which adapters are currently active. This modular approach means if, say, ChatGPT’s DOM updates break its adapter, it doesn’t affect capturing from Google Docs. Logs from each adapter should be tagged with the site name for easier debugging.

### Background Orchestration and Messaging Design

The background script in ConduitLM is the coordinator that receives content from adapters and sends it to NotebookLM. Given Firefox’s event-page behavior, the orchestration has to be robust against the background going to sleep or restarting:

* **Message Routing:** Define a clear schema for messages. For example, content scripts might send messages like { type: "INGEST\_REQUEST", source: "YouTube", payload: { ... } } to the background. The background then processes and eventually responds with { status: "queued" } or { status: "error", reason: "…"}. Similarly, if the background needs to request more info from a content script, it can use browser.tabs.sendMessage(tabId, {type: "QUERY", ...}). All messages should include a type field and perhaps a requestId for pairing responses if needed. This explicit structure prevents confusion where the wrong listener picks up a message. In Firefox, where multiple contexts exist (content scripts in each tab, possibly a popup script, etc.), having one background listener that switches on message.type is a good practice[\[36\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=js). It ensures only one code path handles each message type.

* **Ensuring Delivery:** ConduitLM should handle the case where a content script sends a message but the background isn’t alive yet. Normally, runtime.sendMessage will automatically wake the background in Firefox, so that’s handled. However, if content script sends a message and gets no response (e.g., due to missing return true in background), the content script could retry after a short delay or show a prompt. It might also listen for a specific acknowledgement. Designing a handshake (content script sends “ping”, background replies “pong”) on startup can assure both sides that messaging works. If the background needs to initiate communication (rare in MV3 since background has no persistent connection to content by default), it must do so when the content script is known to be active (e.g., after receiving a ping or using tabs.query to find relevant tabs). ConduitLM can maintain a lightweight registry of active tabs: when a content script loads, it sends a “register” message with its tab ID, which the background notes. Then the background knows it can send messages to that tab later if needed, without the risk of “receiving end does not exist”.

* **Retry and Queue Mechanism:** Because the background might unload, any long-running orchestration (like waiting for an external network reply) should not be purely in-memory. If ConduitLM sends data to NotebookLM’s API, it should set a timeout or listen for success/failure. In case of failure (or no response), it should enqueue a retry. The **queue of pending ingestions** should be stored in browser.storage.local or a similar persistent store, as per Rule 1\. The design might involve pushing a task object {id, content, targetNotebook, status} into storage and then using browser.alarms.create for a near-future time (e.g., 1 minute later) to attempt the send. The alarm event will wake the background, which checks storage, finds the pending task, and tries again. This approach is resilient to restarts and aligns with Firefox’s event model (the alarm guarantees a wake-up)[\[2\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Firefox%20106.%20,Change%20timers%20to%20alarms). It effectively decouples the ingestion attempt from the ephemeral background lifetime.

* **Idempotency and Deduplication:** The orchestration layer should consider scenarios like the same content being sent twice (perhaps the user clicked “ingest” twice, or a background retry overlaps with a manual trigger). To avoid duplicate entries in NotebookLM, ConduitLM could implement an idempotency key for each content item. For instance, generate a hash of the content or an identifier (maybe combination of source, timestamp, and a content snippet) and use it to check against recently ingested items. This check can be done either locally (store recent hashes in storage) or if NotebookLM provides an API to query existing notes. If a duplicate is detected, skip or update the existing entry rather than creating a new one. This logic should reside in the background, as it has the global view and storage access.

* **Concurrency and Lifetime:** Since Firefox can suspend the background, ConduitLM should avoid designing any workflow that *assumes* the background stays alive until completion. Instead, break workflows into event-driven chunks. For example, after initiating a NotebookLM upload (perhaps via fetch() from the background), if the next step is to confirm success, that confirmation might come via the fetch promise resolving. If the background were to unload in between (unlikely while an XHR/fetch is in progress, but possible if the operation takes very long or if Firefox had a bug), an alarm or the fetch’s own promise callback would revive or continue after reload. In practice, event pages won’t unload mid-API-call; they unload when idle. So keeping some console.log or minor no-op operations during a long network call isn’t necessary – just ensure that after the call finishes, you persist the result. Also, use runtime.onSuspend if needed for cleanup (but remember it can’t guarantee async ops finish)[\[37\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onSuspend#:~:text=Sent%20to%20the%20event%20page,are%20not%20guaranteed%20to%20complete). ConduitLM might use runtime.onSuspend to quickly save a checkpoint of what it was doing if Firefox decides to unload the background due to extended idle time.

### Ingestion Pipeline to NotebookLM (Reliability Considerations)

The ultimate goal is getting data into NotebookLM, which likely involves either calling a web service or interacting with a Google Docs-based interface. The design should incorporate Firefox MV3 realities for network and integration:

* **Web Requests and CORS:** If NotebookLM exposes an API endpoint (let’s assume something like https://api.notebooklm.google.com/addNote), the extension background can call it using fetch or XHR. Because this is a cross-origin request (from the extension origin to google.com), Firefox will allow it *only if* the extension has host permission for that domain[\[38\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=The%20extra%20privileges%20include%3A). We must include the relevant Google domain in host\_permissions to leverage the relaxed extension CORS rules[\[38\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions#:~:text=The%20extra%20privileges%20include%3A). If NotebookLM has no public API and instead the extension must open a page or use the Google Docs context, the pipeline might be different (e.g., open a hidden tab to a special page and inject content). In either case, ConduitLM should design for robust error handling: network failures, HTTP 500 errors, API quota issues, etc., are all possible. The pipeline should catch errors from fetch() promises and decide whether to retry (with backoff) or log and give up.

* **Auth and Cookies:** Since NotebookLM is tied to the user’s Google account, the extension might rely on the user being logged in via Firefox. If using direct web requests from the background, appropriate cookies or OAuth tokens need to be sent. Firefox will include cookies in a fetch to google.com if the request is made in the context of the extension and the user is logged in (assuming no credentials: 'omit'). However, some Google endpoints might require an OAuth flow. If an OAuth2 process is needed (via identity API or similar), that adds complexity but Mozilla does support browser.identity.launchWebAuthFlow. The design should factor in that initial authentication might be required and tokens stored securely (probably in browser.storage.local with proper permission). The pipeline should verify it has auth (perhaps via a quick endpoint check) and if not, initiate the sign-in process.

* **Hand-off via Content Script (if applicable):** If NotebookLM ingestion is done by simulating user actions (like opening a Google Doc and pasting content), that would involve a different path: the background might open a new tab to a known NotebookLM UI and then use a content script (with appropriate permission) to insert the data. This is more of a fallback if no official API exists. In Firefox MV3, this is doable but requires careful sequencing: open tab \-\> tab loads (need tabs.onUpdated or similar to know when it's ready) \-\> then inject a script (with scripting.executeScript) \-\> perform DOM manipulation. Each step must check permissions and success. The design must ensure to close that tab or indicate to the user what’s happening (maybe a temporary notification). While not ideal, if ConduitLM goes this route, it should treat NotebookLM’s page as another “adapter” target and follow all the same rules (host permission for the domain, content script to do the insertion, etc.). Logging each step (tab opened, script injected, result success) would be essential for debugging this workflow.

* **Transactional Integrity:** Once data is sent to NotebookLM, ConduitLM should ideally confirm it was received to mark the task done. If the API returns a note ID or the content script can verify the note appears, that confirmation can be logged. If confirmation fails or is uncertain, the pipeline might leave the task in a “pending” state and retry later (to avoid dropping data). However, the design should also avoid duplication: if a retry happens, it should either create a new note only if the previous didn’t go through, or possibly update the existing. This ties into idempotency mentioned above. One strategy is to include a unique identifier with each note (maybe in the note content or metadata if possible, like “Source: ConduitLM \[ID: 12345\]”). Then before creating a new note, check if one with that ID exists. The specifics depend on NotebookLM capabilities, but the architecture must anticipate the need for such checks to prevent cluttering the user’s notebook with repeats.

* **Graceful Degradation:** If for some reason NotebookLM is unreachable (network outage, service down) or the user is not signed in, ConduitLM should not lose the data. The design can incorporate a fallback storage for captured content. For example, ConduitLM might maintain a local cache of the last N items captured but not yet uploaded. This could even be presented to the user (maybe through a page or popup) with a “Retry All” button. Essentially, the pipeline should ensure that once the extension has grabbed data from a source, that data is either safely delivered to NotebookLM or remains available in extension storage until it can be delivered. This might mean storing text (which could be large if it's an article or transcript – be mindful of browser.storage.local quotas, which are usually quite generous (5-10 MB) but large videos transcripts might approach that). Alternatively, partial data could be stored in IndexedDB if very large. The architecture should note these limits and possibly chunk or compress data if needed.

### Logging and Observability Requirements

Given the complexity of multi-step ingestion and the constraints of Firefox MV3, ConduitLM must include thorough logging and monitoring to ease debugging and provide transparency:

* **Centralized Logging Utility:** Implement a small logging wrapper that can be used in content scripts, background, and other contexts uniformly (e.g., a function that prefixes messages with “\[ConduitLM\]\[Background\]” or “\[ConduitLM\]\[YouTube Adapter\]”). This will make it easier to filter in the console. Firefox’s devtools console shows logs from different extension contexts, but labeling them helps, especially when multiple content scripts are active[\[39\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=You%20can%20set%20breakpoints%2C%20step,your%20code%20display%20in%20Console).

* **Log Key Events:** At minimum, log the following events:

* Content script injection attempts (dynamic): log when injecting, and log success or failure (including lastError if any). For manifest content scripts, log in the content script “I am running on domain X”.

* Permission checks: if a content script or background finds a permission missing, log a warning like “Host permission for X not granted – cannot proceed”.

* Messages sent and received: not every single message (could be noisy), but important request/response cycles. For instance, when a content script sends an INGEST\_REQUEST, log on both sides (“Background received ingest request from ChatGPT adapter”). When background finishes processing that request (either queued or uploaded), log the outcome (“Background: ingestion of \[ID\] completed” or “queued for retry”).

* Background lifecycle events: log when the background starts up (runtime.onStartup or just a top-level log "Background script loaded, reason: ...") and when it’s about to suspend (runtime.onSuspend). Firefox will call runtime.onSuspend shortly before unloading; ConduitLM can use this to log “Background suspending, saving state…”[\[37\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onSuspend#:~:text=Sent%20to%20the%20event%20page,are%20not%20guaranteed%20to%20complete). Even though asynchronous operations may not complete in onSuspend, a quick sync log or state dump is possible.

* External interactions: log NotebookLM API calls (e.g., “POST /addNote sent, awaiting response”), and the results (success or error code). Be cautious not to log sensitive info (user content) in verbose detail if the logs could be exposed, but for developer debugging it’s fine. Perhaps allow a debug flag that turns detailed content logging on/off.

* **Use of Browser Toolbox and DevTools:** Document for developers how to inspect ConduitLM in Firefox’s developer tools. For instance, note that background logs will appear in the extension’s debug console (opened via about:debugging)[\[40\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=,of%20data%20stored%20by%20the)[\[41\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=This%20console%20shows%20messages%20from,messages%20at%20Viewing%20log%20output), while content script logs show up in the page’s console (and to see them one must enable “Show content scripts” in the DevTools source list)[\[42\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=Content%20scripts%20may%20not%20be,and%20select%20Show%20content%20scripts). In the code, maybe include a one-time tip: if in debug mode, and if running in Firefox, call browser.test.log (if available) or simply console.log instructions for developers to open the right console.

* **Error Reporting:** Some errors might not be visible unless caught. For instance, a promise rejection in background (like a fetch failure) would normally appear in the background console, but to be safe, ConduitLM can catch such errors and console.error them with context. This way, even if multiple retries mask a failure, the log retains history of the attempt. Also, when using browser.runtime.lastError, always output it when present, e.g., if (browser.runtime.lastError) console.error("lastError:", browser.runtime.lastError.message) so that no silent failures slip by.

* **Analytic Logging (Optional):** While not strictly part of Firefox MV3, ConduitLM could maintain a usage log in memory or storage for the last few actions (not for users, but for developers). For example, an array of the last 10 ingestion events with timestamp, site, size, result. This could even be exposed via a debug page or triggered to output in the console via a command (like if the developer types localStorage.getItem('conduitlm\_log') or some debug method). This is helpful for diagnosing issues reported by users after the fact, though one must be careful not to violate privacy or store content long-term without user consent. For our development purposes, assume this is just a tool during testing.

* **Observability in Production:** If ConduitLM will be released, consider toggling verbose logging off or to a reduced level when not in developer mode. Firefox doesn’t have a concept of “developer mode” for installed extensions like Chrome does, but we can base it on an internal flag or build config. In any case, ensure that critical errors (like permission missing, or NotebookLM upload failed) still surface somehow – possibly by using browser.notifications.create to alert the user in a user-friendly way. That crosses into UI, but from an architecture perspective, the system should not fail silently on important issues. Logging is the developer-facing side of that, whereas user-facing error handling is also important (e.g., if an ingestion can’t complete, notify the user so they’re aware data wasn’t saved).

In summary, ConduitLM’s design will include a **comprehensive logging strategy** to track the flow from content capture to cloud upload. This not only aids debugging in the tricky multi-context environment (background vs content vs network) but also acts as a verification mechanism at runtime – by reading the logs, one can trace exactly what happened, which is invaluable given MV3’s asynchronous, event-driven nature.

## E. Validation Checklist

Before shipping ConduitLM (or even before each merge), the following checklist should be reviewed to ensure the extension meets Firefox MV3 requirements and ConduitLM’s reliability goals:

**Manifest & Permissions:**

* \[ \] **Manifest Version:** manifest\_version: 3 is set. Confirm no legacy keys (like background.persistent) are present (Firefox would error if persistent: true in MV3)[\[43\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=A%20).

* \[ \] **Background Script Configuration:** Firefox **does not** support background.service\_worker – ensure the manifest includes a fallback. For a Firefox-first approach, use "background": { "scripts": \["background.js"\] }. If maintaining cross-browser support, include both "scripts" and "service\_worker" with "preferred\_environment" specifying Firefox should use the document script[\[6\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,service_worker)[\[44\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=is%20not%20specified%20or%20the,service_worker). Test in Firefox that the background script actually runs on startup (e.g., log something in console).

* \[ \] **Host Permissions:** All domains that ConduitLM interacts with are listed in host\_permissions. This includes the content source sites (ChatGPT’s domain, YouTube’s domain, Google Docs, etc.) and any destination or API domains (NotebookLM, which might be under google.com). Ensure patterns are specific (least privilege) – e.g., use https://www.youtube.com/\* instead of broad \*://\*.youtube.com/\* if only the main site is needed, and include subdomains if required (like accounts.google.com if OAuth is needed). Remember that content\_scripts.matches act as host permissions too[\[16\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=host_permissions%20and%20optional_host_permissions%20keys,on%20an%20ad%20hoc%20basis), so double-check both sections.

* \[ \] **Optional Permissions:** If using optional\_host\_permissions for certain sites, verify those are correctly declared and that the extension logic requests them at runtime. Ensure no required functionality is gated behind an optional permission that is never requested. Also verify the user experience: when a permission is needed, browser.permissions.request is called with the right origin pattern and the extension handles acceptance or rejection gracefully.

* \[ \] **Permissions Key:** Check non-host permissions as well. For example, "tabs" permission if ConduitLM needs to query tab URLs or open/close tabs; "storage" (though storage is available by default, persistent storage usage is expected); "alarms" (no permission needed, just the API); "scripting" (mandatory for dynamic script injection)[\[8\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Scripting%20API); "notifications" if user notifications are used; "identity" if using Google OAuth. Remove any permissions not actually needed to minimize attack surface.

* \[ \] **browser\_specific\_settings (Gecko ID):** Since ConduitLM will be released on AMO, ensure the manifest has a browser\_specific\_settings.gecko.id (or legacy applications.gecko.id) set to a unique add-on ID. Firefox requires an explicit ID in MV3 for signing/distribution[\[45\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=match%20at%20L1579%20to%20use,sure%20to%20add%20one%20in). This is often overlooked and will cause the extension to be unsigned or fail submission if missing.

* \[ \] **Content Security Policy:** If the extension injects any scripts or uses eval (it shouldn’t in MV3), verify the CSP in the manifest. MV3 in Firefox requires moving the CSP under content\_security\_policy.extension\_pages[\[46\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Content%20security%20policies). Check that no prohibited directives are used: MV3 disallows remotely hosted code and inline scripts; ensure no 'unsafe-eval' or external script origins are present[\[27\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=Manifest%20V3%20has%20a%20more,further%20changes%20in%20your%20pages). If ConduitLM uses WebAssembly, 'wasm-unsafe-eval' must be included[\[47\]](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/#:~:text=content_security_policy%20field%20no%20longer%20supports,other%20parts%20of%20the%20extension). Typically, a simple CSP like "default-src 'self'; img-src 'self' data:; media-src 'self' data:" should suffice (adjust if the extension loads local images or media). Run web-ext lint to catch CSP and manifest issues automatically.

**Content Script Injection & Execution:**

* \[ \] **Manifest Content Scripts:** Verify that all statically declared content scripts have correct matches patterns and that their files are listed in the manifest.json. Check run\_at (default is document\_idle) – if ConduitLM needs earlier injection (e.g., to catch page load events or dynamically loaded content), consider document\_end or document\_start as appropriate. Ensure "all\_frames": true is set if the content script needs to operate in iframes (for example, YouTube embeds or if Google Docs uses iframes for editor). If not needed, leave it false to reduce injection surface.

* \[ \] **Dynamic Injection Logic:** For any site where content scripts are injected via browser.scripting.executeScript, test that path thoroughly. Use a test page or the real target:

* Call the injection function from the background and confirm it returns a promise that resolves with no error. If lastError is set (catch it), there’s likely a host permission issue or an execution issue.

* Confirm that the injected script actually runs: e.g., have it do a console.log("ConduitLM script injected"). Open the page’s devtools and ensure that log appears, or use browser.tabs.executeScript in dev with a simpler script to verify injection works.

* Test injection on a site with permission vs the same site without permission (revoke it) to ensure the error is properly caught and handled (the extension should maybe prompt for permission if not granted).

* \[ \] **Content Script Messaging:** Each content script should attempt to communicate with the background (even if just on demand). Verify that on script load, if it’s supposed to send a “ready” or “hello” message, that message is received by the background. Use console logs on both sides (content script and background) to track this. If a content script is supposed to respond to messages from background, send a test message using browser.tabs.sendMessage and see that the content script’s listener fires and responds.

* \[ \] **No Restricted Domains:** Ensure content scripts are not set to inject into Mozilla’s restricted domains (like addons.mozilla.org)[\[48\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=Restricted%20domains)[\[49\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#:~:text=In%20Firefox%2C%20this%20includes%20these,domains) or other disallowed pages (Chrome Web Store, etc.). These should be filtered out in matches. If any match pattern accidentally included one (like \*://\*.mozilla.org/\* broadly), refine it. This prevents silent failures and potential review issues. (ConduitLM’s targets likely don’t include these, but this is a sanity check.)

* \[ \] **Performance Check:** If ConduitLM injects scripts into pages with heavy content (like very large documents or video pages), ensure the content script is efficient. While not a strict pass/fail, use Firefox’s profiler or simply observe if the page’s performance suffers. Content scripts should generally yield (not block the main thread too long) especially at document\_idle. Quick DOM reads and message posting is fine.

**Messaging & Async Behavior:**

* \[ \] **onMessage Handlers:** For every browser.runtime.onMessage.addListener in the extension (background or elsewhere), verify its implementation:

* If it returns a Promise or calls sendResponse asynchronously, ensure it returns true (for callbacks) or is an async function (which implicitly returns a Promise). Check that no code path calls sendResponse after the listener returns without that safeguard. A good practice is to always return something: either false/undefined for no async response or a Promise/true if expecting to respond later[\[14\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage#:~:text=To%20send%20an%20asynchronous%20response%2C,there%20are%20two%20options). Do a code review focusing on each listener.

* If multiple scripts are adding onMessage listeners, confirm that they listen for distinct message patterns to avoid interference. For example, the background might handle {type:"INGEST\_\*"} messages and a popup might handle {type:"SHOW\_UI"} messages. They shouldn’t both accidentally handle the same message. If there’s any overlap, consider consolidating or adding logic to prevent double responses.

* \[ \] **Long-lived Connections:** If using browser.runtime.connect (ports) for e.g. streaming data or keeping the background alive during a sequence, test that thoroughly. Open the extension’s background console and content script console:

* Ensure that port.onMessage listeners are set on both sides.

* Send test messages through the port and verify receipt.

* Check that when the content script (or the relevant page) unloads, the background gets a runtime.onDisconnect event on that port. The background should handle it (maybe cleaning up any related state). If the background initiates a disconnect, ensure the content side handles it if needed.

* Critically, ensure no port remains open unintentionally after operations. After an ingestion is done, the content script should disconnect (or background disconnects) so that the background can eventually unload. You can check active ports by instrumenting code or simply knowing that if runtime.onSuspend never fires, maybe a port is left open. Another method: call browser.runtime.getBackgroundPage (if it exists in MV3 for event pages) or see in about:debugging if the extension stays perpetually running.

* \[ \] **Error Handling in Messaging:** Induce some failures to see if they’re handled:

* Send a message from a content script when the background is not listening (if possible) to see if the content script code handles a missing response (it should time out or get a lastError).

* Conversely, have the background send a message to a tab with no content script and ensure the promise is rejected or lastError is checked. ConduitLM might not normally do this, but testing the error path ensures stability (no unhandled promise rejections, etc.).

* If any messaging promises are used (browser.runtime.sendMessage().then(...)), ensure there’s a .catch(...) attached or using try/await within a try-catch, so that if lastError occurs, it’s caught and logged, not silently ignored.

**Background Script Lifecycle & Persistence:**

* \[ \] **State Persistence:** Simulate a Firefox restart or background unload:

* With the extension loaded in about:debugging, click the “Reload” button for the extension – this effectively restarts the background script as if the browser was restarted. After reload, check that any pre-existing state (e.g., queued tasks, saved preferences) was properly loaded from browser.storage.local. If ConduitLM is supposed to resume an upload, verify that logic triggers on startup (perhaps via runtime.onStartup). Use console logs to confirm (e.g., “Restored X pending tasks from storage”).

* During normal operation, let the extension go idle: do not interact with it for a couple of minutes. Then trigger an action (like use the browser action or send a test message from a content script) and see if the background logs indicate it was re-initialized (you might see logs that run only on fresh start). If so, confirm that nothing critical was lost due to that idle-unload. If something was lost, tighten the auto-save frequency of that data.

* Check that browser.alarms are used for any periodic work. Use the about:debugging “Inspect” on the extension, go to the Console and type browser.alarms.getAll().then(console.log). Confirm that expected alarms are scheduled (for retries or maintenance tasks). Make sure their names and due times align with the design (e.g., an alarm for each queued item or a single alarm for a batch).

* If using runtime.onSuspend, verify it’s wired up. You can’t easily force suspend except by idling, but you might simulate by calling the handler manually in code for test. Ensure it doesn’t attempt anything disallowed (like lengthy async work).

* \[ \] **Multiple Browser Windows / Sessions:** Open a second Firefox window or a Private Window and trigger extension actions there. The event-page model should handle this seamlessly (the background is shared singleton, content scripts can be in multiple windows). Verify that concurrency doesn’t cause issues: e.g., ingest two different pages nearly simultaneously and see if both get handled. The background should queue them appropriately. Look for any interleaving issues or race conditions in logs.

* \[ \] **Resource Cleanup:** Use Firefox’s about:performance or about:memory to check for leaks. After running a series of ingestions and closing those tabs, ensure the extension isn’t holding onto references (memory should drop, no “ghost” tabs associated with extension in about:memory’s extension compartments). The presence of "dead object" errors (addressed above) would indicate a problem; absence means likely okay. Also confirm that no excessive CPU usage in background when idle (should be zero when nothing happening).

**Debugging and Dev Workflow:**

* \[ \] **Content Script Debugging:** Open a target page (e.g., YouTube), open DevTools on that page, go to **Debugger**, click the gear icon and ensure "Show content scripts" is enabled[\[42\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=Content%20scripts%20may%20not%20be,and%20select%20Show%20content%20scripts). Verify that ConduitLM’s content script appears in the source list (usually under a section like “Extension Scripts”). Set a breakpoint in the content script (e.g., at the entry point of its main function or message listener) and refresh the page. Confirm the breakpoint hits, which means the content script is indeed running at the expected time. This also helps ensure that the content script isn't throwing exceptions early (which you might catch in the debugger if it pauses on exceptions).

* \[ \] **Background Inspection:** In about:debugging, click **Inspect** for ConduitLM to open the background’s devtools. In the Console, verify that any startup log messages from the background are present, indicating the background loaded. Check the **Debugger** panel in that toolbox to see your background script and that you can set breakpoints. Test reloading the extension (via about:debugging) with the toolbox open to see that it reconnects properly and you can still hit breakpoints in early initialization code. Use the **Storage** panel to inspect Extension Storage (which is browser.storage.local) to confirm your persisted data is there and has expected values after doing some operations[\[50\]](https://extensionworkshop.com/documentation/develop/debugging/#:~:text=We%20use%20the%20annotate,examples%20repository).

* \[ \] **Popup / UI (if any):** If ConduitLM has a browser action popup or sidebar, open it and use about:debugging’s **Inspect** to open its devtools. Check that all UI elements work and that it can communicate with the background (e.g., clicking a button triggers the expected background action). Ensure the popup doesn’t try to do something forbidden (like use certain APIs not available in that context – unlikely, but e.g. chrome.tabs might not be directly available without permission).

* \[ \] **Extension Logs and Errors:** Open the **Browser Console** (Ctrl+Shift+J) which aggregates logs from the browser and extensions. Look for any messages or errors related to ConduitLM. Address any unexpected errors or warnings:

* Warnings about unchecked lastError should be fixed by adding checks (they appear as yellow warnings in console when an API fails without handling).

* Security/CSP warnings (if some eval or remote script was blocked) should be resolved by adjusting code or manifest.

* Any runtime exceptions from the extension should be investigated and fixed, even if things “seem to work,” because they might indicate edge cases not handled.

* \[ \] **web-ext Lint & Automated Tests:** Run web-ext lint on the extension. Ensure zero errors and ideally zero warnings. Mozilla’s linter will catch known issues (like using forbidden APIs, incorrect manifest syntax, missing ID, etc.). Additionally, if possible, write a few automated selenium or web-ext run \--browser-console tests where you simulate opening a page and triggering ingestion, then verifying the extension’s state (this is more for development QA, but it can be part of the pre-release).

* \[ \] **AMO Review Readiness:** Check that the extension’s manifest and usage align with Mozilla’s add-on policies. For example, ensure you have a good description for permissions (“why does ConduitLM need access to X site” – this goes in the manifest as optional\_permissions descriptions or in the listing). While not a technical requirement, it speeds up review. Also verify no use of eval or dynamic code (MV3 disallows it and it’s a common review issue).

* \[ \] **Cross-Browser Sanity (if applicable):** As a final step, if the intention is to also release on Chrome, load the same extension package in Chrome (or Edge) and verify basic functionality. Chrome might throw errors for any Firefox-specific manifest keys (like browser\_specific\_settings – Chrome will ignore that) or if something is slightly different in API. Ensuring ConduitLM works on Chrome is outside Firefox scope, but it’s good to know that nothing in the Firefox-specific implementation inadvertently breaks Chrome’s execution (e.g., presence of both background scripts and service\_worker might confuse older Chrome versions – Chrome MV3 prior to 121 would reject an extension that still had a background.scripts key, but from Chrome 121+ it ignores it[\[51\]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#:~:text=,see%20%2093%20Firefox%20bug)).

By walking through this checklist, the ConduitLM team can be confident that the extension respects Firefox’s MV3 model and is robust against common pitfalls. Each item either prevents a known failure mode or verifies an important behavior, thereby acting as a guardrail before the extension is published to users.
